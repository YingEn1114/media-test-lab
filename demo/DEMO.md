# 自动化测试演示脚本（10 分钟）

> 目标：让领导在 10 分钟内看到一套**可重复、可量化、可追溯**的自动化测试能力，而不是一堆脚本。
> 演示环境：本机平台 http://127.0.0.1:8090/ （被测站点：正观新闻 www.zhengguannews.cn）

---

## 0. 演示前 30 分钟检查清单

| 项 | 命令 / 动作 | 通过标准 |
|---|---|---|
| 平台在线 | `cd zgnews-tests && ./start.sh` | 打开 http://127.0.0.1:8090/ 显示总览 |
| 预热跑一次 | 平台“运行全部”或 `pytest tests -q` | 33 passed, 5 xfailed，无 failed |
| 演示用例就绪 | 用例库搜索 `test_homepage`、`test_video_play_pause`、`test_video_mobile_layout` | 能勾选 |
| 浏览器 | 本机 Chrome 可用、已登录站点无弹窗 | headed 能弹出窗口 |
| 离线兜底 | 打开 `demo/evidence/index.html` 与最近一份 Allure | 断网也能展示 |
| 投屏 | 浏览器 100%，16:9，隐藏书签栏 | 关键数字不被裁切 |
| 干扰 | 关闭微信/钉钉通知、系统勿扰 | 演示中不弹窗 |

**演示前最后 5 分钟不要改代码、不要跑全量**，避免站点波动影响现场。

---

## 1. 时间轴（10 分钟）

### 0:00–0:40 开场定位（40 秒）

讲解词：

> 这是一套面向正观新闻的**外部黑盒自动化测试**：38 条用例，覆盖 12 个测试域，一次全量约 2–3 分钟。  
> 它解决三个问题：发布前快速回归、问题可复现、结果可归档。今天用 10 分钟演示“怎么跑、看什么、发现了什么”。

### 0:40–2:00 总览：先看结论（80 秒）

打开 http://127.0.0.1:8090/

指四个数字：

| 指标 | 当前值 | 讲解 |
|---|---|---|
| 用例总数 | 38 | 自动发现，新增 `test_*.py` 即出现 |
| 有效通过率 | 100% | 33/33 有效用例通过 |
| 最近状态 | passed | 全量通过 |
| 最近耗时 | 154.1s | 一次全量约 2–3 分钟 |

再指趋势图与覆盖条：

> 趋势按“有效通过率”算，**xfail 不计入分母**，避免把已知问题算成失败或通过。  
> 覆盖 12 个测试域：首页导航、列表详情、搜索、H5、SEO、安全、接口、性能、可访问性、视频、组件、频道。

### 2:00–3:30 用例库：看资产结构（90 秒）

点“用例库”：

1. 说明左侧文件即用例，右侧是 `cases.json` 里的名称/描述/优先级/标签；
2. 优先级选 **P0**，展示冒烟集；
3. 指 `test_video.py`：8 条播放器用例（元数据、播放暂停、seek、音量、控件、MP4 Range、移动端）；
4. 指 `test_http_api.py`：HTTP 契约、HEAD、robots、CDN、软 404 —— 说明不只测页面。

讲解词：

> 用例是代码资产，不是平台里的手工步骤；代码可 review、可复用、可进 CI。

### 3:30–6:30 现场运行：看执行过程（3 分钟）

在用例库：

1. 搜索并勾选 3 条：
   - `tests/test_home.py::test_homepage`（P0，正常通过）
   - `tests/test_video.py::test_video_play_pause`（P1，播放器）
   - `tests/test_video.py::test_video_mobile_layout`（P1，已知问题 xfail）
2. 勾选 **“显示浏览器”**，慢动作 **700ms**；
3. 点 **“运行选中”**，自动跳到“运行与日志”。

讲解（边看日志边说）：

> 平台用 pytest 子进程执行，日志实时回传；失败会自动截图。  
> 这里能看到每条用例的开始/通过/xfail，以及耗时。  
> 移动端这条会显示 xfail：不是跳过，是**已复现的站点问题**，下面会讲。

预期：约 20–40 秒结束，状态 `passed`，页面上出现 **HTML 报告 / Allure 报告** 两个链接。
如果时间紧，改点 **冒烟运行**（8 条核心用例，约 20–40 秒），话术不变。命令行等价：`pytest -m smoke -q`。

> 如果现场网络慢：不要等，直接说“结果已经预跑过”，跳到报告页。

### 6:30–8:30 报告：看证据链（2 分钟）

点 **Allure 报告**：

1. Overview：38 tests、33 passed、5 skipped（xfail）；
2. Suites：按文件分组，能定位到 `test_video.py`；
3. 点开一条用例：步骤、耗时、失败附件（截图/trace）；
4. 回到平台“测试报告”：说明每 run 同时留 pytest HTML（单文件、可离线）与 Allure（交互式）。

讲解词：

> 一次运行，三种产物：实时日志、pytest HTML、Allure。  
> HTML 适合归档和邮件，Allure 适合定位和汇报；历史里都能点开。

### 8:30–10:00 发现的问题与价值（90 秒）

先打开平台“已知问题”页 http://127.0.0.1:8090/defects （P1/P2 筛选、证据缩略图），再打开 `demo/evidence/index.html`；领导要带走时发 `demo/Defect-Cards.pdf`。

5 个已确认问题，逐条一句话：

| 编号 | 问题 | 一句话证据 |
|---|---|---|
| A06 | 搜索被重定向到下载页 | `/search.html/正观` → 302 → `/down.html` |
| A19 | 未知路径软 404 | 随机路径返回 **200**，正文 22 字节 404 |
| A20 | sitemap 软 404 | `/sitemap.xml` 返回 **200 + text/html**，内容是 404 |
| A29 | 特殊字符搜索同样跳下载页 | `测试<>&%20...` → `/down.html` |
| V08 | 移动端播放器溢出 | 390 视口下 video 固定 **1240px**，页面横向滚动 **1412px** |

收尾讲解：

> 自动化不只是“跑通”，而是**把问题固定成可复现的证据**。  
> 这 5 条都有截图/响应记录，修复后把 xfail 改回正常断言即可回归。  
> 下一步：缺陷卡片、每日巡检+通知、CI 固化、接口层扩展。

## 3. 高频追问 Q&A

**Q1：100% 通过，是不是没测出问题？**  
A：38 条里 33 条有效用例全过，另外 5 条是**已复现的站点问题**，用 xfail 固定下来、单列展示。口径写在平台设置页：有效用例 = passed + failed，xfail 不计入分母。

**Q2：xfail 是不是把失败藏起来了？**  
A：不是 skip。xfail 是“已知问题”的显式标记，有编号、有截图、有复现步骤；问题修复后我们会改回正常断言，让它变成真正的通过。

**Q3：和 MeterSphere 什么关系？**  
A：MeterSphere 管测试计划、验收用例、缺陷；这个平台是**外部执行器**，负责跑 Python/Playwright 用例并出报告。两者职责分开，不重复建用例。

**Q4：维护成本高不高？**  
A：38 条用例 / 22 个文件，新增一条只要 3 步（写 `test_*.py`、加 `cases.json` 元数据、平台刷新）。站点改版时改选择器即可；已知脆弱点是硬编码的文章/频道 ID，下一步会参数化。

**Q5：能覆盖多少？**  
A：12 个域、50+ 测试点；这是**场景覆盖**，不是代码覆盖率。接口层、视觉回归、多浏览器还在路线图里。

**Q6：为什么不用现成的 TMS？**  
A：MeterSphere CE 不能直接跑 Playwright/Python；完整 TMS（Kiwi/ReportPortal）较重。当前方案轻量、可控、能进 CI，后续需要再接。

**Q7：结果稳定吗？**  
A：串行执行 + 失败截图/trace；依赖外部站点，演示前会预热。下一步加失败重试和每日巡检，把波动和真问题分开。
